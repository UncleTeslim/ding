# Troubleshooting

> [Ding docs](README.md) · [Deployment](DEPLOYMENT.md) · [Backup and restore](BACKUP_AND_RESTORE.md) · [Upgrading](UPGRADING.md) · **Troubleshooting**

Start with the service state and recent logs:

```bash
docker compose ps
docker compose logs --tail=200 ding
curl -i http://127.0.0.1:3000/health
```

Use the section that matches what you see. When asking for help, share the status and relevant error lines, but remove passwords, hashes, JWT secrets, and the contents of `.env` first.

## The image does not build

Check the first error in the build output. Then confirm that Docker is running and that the checkout contains the lockfile:

```bash
docker info
git status
docker compose build --no-cache
```

If the error mentions Docker Hub or a network timeout, retry when the server has internet access. If it mentions a missing file, make sure the command is being run from the Ding directory.

## The container is unhealthy or `curl` says “Empty reply from server”

This usually means Ding stopped while starting. Read the application log rather than repeatedly restarting it:

```bash
docker compose ps
docker compose logs --tail=200 ding
docker inspect "$(docker compose ps -q ding)" --format '{{json .State.Health}}'
```

Look for the first error, especially a configuration error or a SQLite permission error. Once the cause is fixed, start it again:

```bash
docker compose up --build -d --wait
curl --fail http://127.0.0.1:3000/health
```

## Ding exits immediately after setup

Check the generated `.env`. Production requires:

- A non-default admin password hash.
- A long `DING_JWT_SECRET`.
- A long `DING_IP_SALT`.
- An HTTPS `DING_BASE_URL`.

The setup command asks for the public HTTPS URL. If you edited `.env` manually, confirm that each value is valid dotenv syntax and has no trailing comments.

Quotes around values are supported and are generated by `npm run setup`; the generated form is `DING_ADMIN_USERNAME='admin'`. Keep the single quotes, especially around `DING_ADMIN_PASSWORD_HASH`, because Docker Compose interpolates `$` in unquoted and double-quoted values. If a value behaves differently, check for an accidental space, smart quote, trailing comment, or invisible character.

## Docker cannot connect to the daemon

Start Docker Engine on Linux or Docker Desktop on macOS/Windows, then verify:

```bash
docker info
docker compose ps
```

On Windows, an error containing `//./pipe/dockerDesktopLinuxEngine` means the Docker Desktop Linux engine is not reachable. Start Docker Desktop and retry; this is separate from a Ding application error.

## `DING_BASE_URL` or request-blocked errors

`DING_BASE_URL` must exactly match the public address users access, including `https://` and the hostname. Do not add a path, query string, or dashboard route.

If Ding is behind a reverse proxy (the public service that forwards traffic to Ding):

- Forward `Host`, `X-Forwarded-For`, and `X-Forwarded-Proto`.
- Keep `DING_TRUST_PROXY=false` unless the immediate proxy hop is trusted.
- If enabling proxy trust, use the narrowest supported value.
- Ensure the proxy sends HTTPS to the browser and Ding's base URL also uses HTTPS.

For the complete Caddy and Nginx setup, see [Deployment](DEPLOYMENT.md).

## Login loops or secure cookies are missing

Production cookies are marked `Secure`, so access the dashboard through HTTPS, not the container's plain HTTP port. Keep port `3000` bound to localhost and let Caddy, Nginx, Traefik, or another trusted reverse proxy handle HTTPS.

## Port 3000 is already in use

Find the process using the port, or change the host side of the Compose mapping while keeping the container port at `3000`:

```yaml
ports:
  - "127.0.0.1:3100:3000"
```

Update your reverse proxy and health-check commands accordingly.

## `attempt to write a readonly database`

This error occurs during SQLite migrations when `/app/data` is not writable. Ding's default deployment uses the named `ding-data` volume and should not need host filesystem permission changes. Check the effective Compose configuration and logs:

```bash
docker compose config
docker compose logs --tail=200 ding
docker volume ls
```

Make sure `/app/data` is not mounted with `:ro`, and do not add `read_only: true` to the service unless you have explicitly provided every writable runtime path. If you changed storage modes during testing, stop the service and restore from backup before changing or removing any volume. `docker compose down -v` deletes the named volume and its database; it is not a routine troubleshooting command.

## Database unavailable or permission denied

Confirm the volume is mounted and the container is running as the non-root `node` user:

```bash
docker compose ps
docker volume ls
docker compose logs --tail=200 ding
```

Do not mount `/app/data` read-only. If using a host bind mount, make the directory writable by the container user. Do not delete the volume while troubleshooting.

## Data disappeared after a restart

Check that the Compose volume is still present. `docker compose down` is safe; `docker compose down -v` removes the database volume. If the volume was deleted, restore the latest verified backup.

## Widget does not appear

Check the browser network panel and confirm:

- The `widget.js` URL points to the Ding instance.
- The Ding instance is reachable over HTTPS.
- `/api/announcements` returns a successful response.
- At least one announcement is published.
- The host page's CSP allows the Ding script and API origin.
- The embed attributes use supported values.

The widget is intentionally cross-origin, while admin APIs are same-origin.

## Migration errors

Read the first migration error in the logs and stop repeated restarts. Preserve the database before attempting recovery. Verify that the application image contains the migration files and that the volume is writable. For an upgrade-related failure, follow the rollback and restore procedure in [Upgrading](UPGRADING.md).

## Need more help

When opening an issue, include:

- Ding release or Git commit.
- Docker and Docker Compose versions.
- Operating system and architecture.
- The relevant `docker compose ps` output.
- The relevant logs with secrets and credentials removed.
- Whether the deployment uses a named volume or bind mount.
